A `skipif`-green test counts as unverified, not as covered. The roster is `src/yowo/backends/_roster.py`, TOTAL over `BackendType` enumerated at runtime, so a sixth backend cannot be added without a verdict. EXECUTED unmocked against the digest-verified weight in CI: **pytorch, onnx, openvino**. UNVERIFIED with the runner named: **tensorrt** (no PyPI wheel on the standard index, needs an NVIDIA driver and CUDA device at import — a self-hosted GPU runner) and **coreml** (compiles and executes only on macOS — a macos-latest runner, sequenced into `ci-matrix`). Measured 2026-09-13 before the work: exactly ONE backend was executed unmocked anywhere, and coverage read `_openvino.py` 21%, `_pytorch.py` 58%, `_tensorrt.py` 73%, `_onnx.py` 77%, with no `test_pytorch_backend.py` at all. OpenVINO's 21% had a cause worse than neglect: it could not run on ANY OpenVINO >=2025. `_openvino.py:102` imported `Core` from `openvino.runtime`, a module removed in 2025, and the handler relabelled the ImportError as `DependencyError("openvino", "uv add openvino")` — telling a user to install a package they already had, while `ov.Core()` reported `['CPU']` and compiled the model in the same process. Behind that sat a SECOND bug: `input_node.shape` raises `to_shape was called on a dynamic shape`, and yowo's own `export_model` defaults to `dynamic_batch=True`, so our own export produced an IR our own backend could not read. Both are fixed here and proved by executing OpenVINO on a real weight, not by reading the import. RESIDUAL, named rather than hidden: tensorrt and coreml remain unexecuted, so nothing here says they work   (← backend-conformance-suite)
- [x] A shared parametrized conformance suite asserts identical behaviour across the backends CI can run — output shape/dtype, empty detections, class mapping, error type on bad input — with the tolerance stated before the run and the actual deviation reported. `tests/integration/test_backend_conformance.py` drives pytorch, onnx and openvino from ONE artifact chain rooted in the digest-verified weight, so the three are KNOWN to hold the same weights rather than assumed to. Tolerance declared BEFORE the run: **1e-3 absolute on box coordinates, exact on class ids**. Deviation actually measured, PyTorch vs ONNX on bus.jpg, both pinned cpu/fp32 — and it is a PLATFORM SPLIT of ~2100x, which is the finding: **ubuntu-latest x86_64 0.00015450 px (inside the bound)**, **macOS 15 arm64 0.33050537 px (330x the bound)**. Counts (5 and 5) and class-id mismatches (0) agree on both. CI runs x86_64, where the backends conform — which is what this box claims, since its own words scope it to "the backends CI can run". CORRECTED 2026-09-13: this box was first recorded as BUILT-BUT-NOT-TICKED on the arm64 figure alone, and the suite pinned that figure as if it were a property of the code. CI refused it — a strict xfail XPASSed and the pinned-deviation check reported `0.00015450 vs 0.33050537`. The original conclusion, "the models are the same model and the arithmetic differs", was wrong as a general claim, and the BN-fusion hypothesis with it: fusion is platform-independent. The suite now asserts only the declared bound, records both platform figures as documentation rather than assertions, and carries a strict xfail scoped to macOS arm64 — so x86_64 must PASS and arm64 must FAIL, and either flipping is a red. RESIDUAL, named rather than hidden: the arm64 divergence is real for anyone developing on Apple Silicon and is NOT explained; it is owned by `pytorch-onnx-numeric-divergence` in m4-honest-deployment. Nothing here says the two backends agree on arm64, because they do not   (← backend-conformance-suite)
