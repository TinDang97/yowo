## CARD
goal: Every claim yowo makes about inference has a runnable, committed check behind it.
why: 2175 tests and 80% line coverage prove things about mocks. The product's entire value rests on evidence that does not exist in the repository. AMENDED 2026-09-13, measured rather than restated, because m2 and m1 closed three of the five claims this milestone was written on and building against a stale motivation is how a node ends up justifying work the repo already did: (i) "No test executes a real backend forward pass" is FALSE — `tests/integration/test_real_backend_smoke.py` runs PyTorch on bus.jpg in the `Real Backend Smoke` CI job, delivered by m2's `real-backend-smoke`; (ii) "OpenVINO is at 0%" is FALSE — it is 21%, and the reason it is only 21% turned out to be far worse than low coverage: the backend could not run AT ALL on OpenVINO >=2025, see box 1; (iii) "the integration tier is gated on one developer's home directory" is FALSE — `tests/integration/conftest.py` keys on `YOWO_CACHE_DIR` with a `~/.cache` default, delivered by m1's `ci-weight-fixture`. ## EXIT
- [x] Every backend `create_backend()` can return is either constructed and executed by a test, or named in a committed unverified list with its reason and the runner it would need. A `skipif`-green test counts as unverified, not as covered. The roster is `src/yowo/backends/_roster.py`, TOTAL over `BackendType` enumerated at runtime, so a sixth backend cannot be added without a verdict. EXECUTED unmocked against the digest-verified weight in CI: **pytorch, onnx, openvino**. UNVERIFIED with the runner named: **tensorrt** (no PyPI wheel on the standard index, needs an NVIDIA driver and CUDA device at import — a self-hosted GPU runner) and **coreml** (compiles and executes only on macOS — a macos-latest runner, sequenced into `ci-matrix`). Measured 2026-09-13 before the work: exactly ONE backend was executed unmocked anywhere, and coverage read `_openvino.py` 21%, `_pytorch.py` 58%, `_tensorrt.py` 73%, `_onnx.py` 77%, with no `test_pytorch_backend.py` at all. OpenVINO's 21% had a cause worse than neglect: it could not run on ANY OpenVINO >=2025. `_openvino.py:102` imported `Core` from `openvino.runtime`, a module removed in 2025, and the handler relabelled the ImportError as `DependencyError("openvino", "uv add openvino")` — telling a user to install a package they already had, while `ov.Core()` reported `['CPU']` and compiled the model in the same process. Behind that sat a SECOND bug: `input_node.shape` raises `to_shape was called on a dynamic shape`, and yowo's own `export_model` defaults to `dynamic_batch=True`, so our own export produced an IR our own backend could not read. Both are fixed here and proved by executing OpenVINO on a real weight, not by reading the import. RESIDUAL, named rather than hidden: tensorrt and coreml remain unexecuted, so nothing here says they work   (← backend-conformance-suite)
- [ ] A shared parametrized conformance suite asserts identical behaviour across the backends CI can run — output shape/dtype, empty detections, class mapping, error type on bad input — with the tolerance stated before the run and the actual deviation reported   (← backend-conformance-suite)
      BUILT BUT NOT TICKED 2026-09-13, by human decision. The suite exists and CI runs it: `tests/integration/test_backend_conformance.py` drives pytorch, onnx and openvino from ONE artifact chain rooted in the digest-verified weight — so the three are KNOWN to hold the same weights rather than assumed to — and asserts all five axes this box names. The tolerance was declared before the run: **1e-3 absolute on box coordinates, exact on class ids**. The deviation actually measured, PyTorch vs ONNX on bus.jpg, both pinned cpu/fp32: counts **5 and 5**, class-id mismatches **0**, max coordinate deviation **0.33050537 px**, max confidence deviation **0.00726026** — 330x the declared bound. The bound was NOT moved to fit it; the numeric case is a `xfail(strict=True)` carrying the measured figure, so the assertion and the bound are unchanged, the gap is visible, and CLOSING it turns the suite red until the marker is removed. This box stays unchecked until that divergence is closed, because a box that reads 'identical behaviour' while the behaviour differs by 330x its own tolerance would be false. Owner: `pytorch-onnx-numeric-divergence` in m4-honest-deployment. m3's own risks anticipated exactly this: 'expect the parity and equivalence suites to go red on first run; that is success, and the fixes belong to m4.
