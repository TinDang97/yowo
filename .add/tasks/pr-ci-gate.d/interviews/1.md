# interview 1 — pr-ci-gate

## A1 [who]
- asked: the GitHub default — it runs, with a read-only token and no secrets — because this workflow needs no secrets
- if wrong: an outside contributor's PR shows no checks and looks unreviewed.
- answered: confirm

## A2 [who]
- asked: "nobody, including the repository owner" (`enforce_admins: true`) because a solo maintainer with bypass is the state the repo is in today
- if wrong: the gate is advisory and the finding it fixes returns quietly. · found: decided by the human at freeze, 2026-09-08 — `enforce_admins: true`, with the emergency path being to disable protection in settings, merge, and re-enable, which is visible in the audit log. No longer a priced guess.
- answered: confirm

## A4 [which]
- asked: "no path filter — every PR runs the gate", because a `paths-ignore` that skips docs would have skipped this very PR and the repo has no reliable docs/code split
- if wrong: CI minutes are spent on documentation-only PRs. Cheap to reverse.
- answered: confirm

## A5 [which]
- asked: "left untouched, and `ci.yml` is additive", because renaming it would break the `release` job's `needs: [quality]`
- if wrong: the two gates drift apart, which R:DIVERGENCE exists to catch.
- answered: confirm

## A6 [which]
- asked: "the single `ci.yml` job is the one required check", because per-step required checks do not exist in GitHub
- if wrong: a human configures a check name that never appears and the branch is unprotected while looking protected.
- answered: confirm

## A7 [when]
- asked: `on: pull_request` default activity types (`opened`, `synchronize`, `reopened`) so every new commit is gated
- if wrong: a PR is approved on a commit that was never tested.
- answered: confirm

## A9 [when]
- asked: "the workflow lands and runs green on at least one PR FIRST, then this task enables protection via the API", because GitHub will not accept a required-check context it has never observed
- if wrong: the API call succeeds with a context that never reports and every subsequent merge blocks forever. This ordering is the whole reason protection cannot be enabled in the same step that creates the workflow.
- answered: confirm

## A10 [absent]
- asked: "the job fails", which is the default
- if wrong: low cost, this is the desired behavior.
- answered: confirm

## A11 [absent]
- asked: "it appends a NEW id rather than reusing one", because reuse silently changes what an existing required check means
- if wrong: a required check named `quality` starts asserting something the branch-protection setting was never approved for.
- answered: confirm

## A12 [absent]
- asked: "this task enables it via `gh api -X PUT`, with the payload approved by the human before it runs, and `scripts/verify_branch_protection.py` asserting the live result", because `main` is currently unprotected — `gh api repos/TinDang97/yowo/branches/main/protection` returns 404 and `rulesets` returns `[]`
- if wrong: the milestone's exit box reads as satisfied by a file that gates nothing. · found: main has no branch protection and no rulesets (evidence: `gh api repos/TinDang97/yowo/branches/main/protection` → 404 "Branch not protected"; `gh api repos/TinDang97/yowo/rulesets` → `[]`, 2026-09-08).
- answered: confirm

## A13 [order]
- asked: "one job, steps in `release.yml`'s existing order (lint, format, types, tests)", because a single job is a single required check and cheap steps failing first is the useful ordering
- if wrong: a slow test run masks a one-second lint failure.
- answered: confirm

## A14 [order]
- asked: "no `needs:` between appended jobs unless a later task declares one", so the six appenders stay independent
- if wrong: one slow appended job serializes the whole gate.
- answered: confirm

## A16 [experience]
- asked: "the failing step's own output, no summary layer", because adding a reporting layer is scope this task does not have
- if wrong: a contributor reads a 15-minute pytest log to find one lint error. Mitigated by A13's ordering.
- answered: confirm

## A17 [experience]
- asked: "a comment block at the top of `ci.yml` naming the frozen ids and the append rule", because a convention documented outside the file it governs is not read
- if wrong: six tasks each invent their own structure and the collision this task exists to prevent happens anyway.
- answered: confirm

## A18 [experience]
- asked: "exact check name, exact setting path, and the `enforce_admins` decision, written in the repo", because a half-remembered setting is the failure mode here
- if wrong: protection is enabled with the wrong check name and merges are blocked on a check that never reports.
- answered: confirm

## A19 [absent]
- asked: "plain `uv sync --group dev`, mirroring `release.yml`", NOT `--locked`, because `uv lock --check` reports the committed lockfile already needs updating, so `--locked` would fail every PR from day one
- if wrong: CI silently re-resolves dependencies the lockfile claims to pin, and a PR is tested against packages `uv.lock` does not name. · found: `uv lock --check` → "The lockfile at `uv.lock` needs to be updated" (2026-09-08); local uv 0.10.11 writes `revision = 3`, committed lock is `revision = 2`. Filed as specs/quality Q1; refreshing the lock is its own node, not this one.
- answered: confirm

## R:SILENT_PASS [reject]
- asked: A job that reports success while its command did not run — a `continue-on-error`, an `|| true`, or a step skipped by a condition that is always false.
- answered: confirm

## R:DIVERGENCE [reject]
- asked: `ci.yml` and `release.yml` running different versions of the same check, so a PR can be green and `main` red on identical code.
- answered: confirm
