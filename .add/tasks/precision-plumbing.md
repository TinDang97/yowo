## CARD
goal: The precision a caller asks for reaches the backend that executes it, or the caller is told — loudly, naming the backend and the device — that it cannot.
why: Measured at HEAD 714fa79 — `create_backend()` has no `precision` parameter at all, so the value `select_backend()` resolves at `engine.py:286` is computed and dropped. `PyTorchBackend(fp16=...)` is the only runtime hook in the library and nothing has ever passed it. The live lie is the asymmetry: an explicit `fp16` on CPU is silently coerced to fp32, but an explicit `int8` is passed straight through `select_precision`'s CPU branch (`_selector.py:181-182`), stored on `BackendSelection`, and published by `health_report().precision_current` while fp32 executes. An operator sizing an edge box reads `int8` off a configuration that never took effect.
beat: done · next: add status

## RULES
<must>
- M1 `create_backend()` carries the resolved precision to the backend it constructs, and the backend acts on it — `PyTorchBackend` autocasts under CUDA because it was told to, not because a default happened to match.
- M2 An EXPLICIT precision request that is not what the loaded backend actually executes raises `ConfigError` at `load()`, and the message names the backend, the device, and an alternative the user can act on.
- M3 An AUTO-SELECTED precision that cannot be honoured is adjusted without raising. No call that works today on an unset `precision` starts failing.
- M4 `health_report().precision_current` is produced by the executing backend and stays typed `str` — no public type changes. When a backend cannot determine what it is executing, the field reads the documented sentinel `"unknown"`, never a value it cannot verify and never the request.
- M5 The precision verdict is TOTAL over `BackendType` — a sixth backend cannot reach `create_backend()` without one, asserted against the enum at runtime, not against a list someone must remember to update.
- M6 The OOM ladder performs a real recovery in every band it claims one, and `degradations_total` counts only recoveries that changed engine state.
- M7 The engine no longer writes a tune profile's `precision` into a production `InferenceConfig`, so a non-`None` `config.precision` means exactly one thing: a human asked for it.
- M8 The explicit request is compared against what EXECUTED, never against `BackendSelection.precision` — selection may silently degrade the request before the comparison ever sees it.
</must>
<reject>
- R:REPORTS_REQUEST A precision is reported that no backend executes — the shipping `int8`-on-CPU defect, restated as a rule so a check must kill it -> "REPORTS_REQUEST"
- R:SILENT_COERCION An EXPLICIT request is answered with a different precision and no error -> "SILENT_COERCION"
- R:AUTO_RAISES An auto-selected precision raises, converting a working default path into a failure -> "AUTO_RAISES"
- R:SWALLOWED_BY_FALLBACK The backend-fallback loop at `engine.py:455-496` re-derives or discards the explicit request and lands on a backend that does not honour it -> "SWALLOWED_BY_FALLBACK"
- R:PHANTOM_DEGRADATION `degradations_total` is incremented for a recovery that did not happen -> "PHANTOM_DEGRADATION"
- R:PUBLIC_BREAK A public NAME disappears OR a public TYPE changes. This node removes nothing and widens nothing: `HealthReport.precision_current` stays `str`, `TuneProfile.precision` stays. If a `__all__` entry or either annotation moves, the node has taken m5's decision for it -> "PUBLIC_BREAK"
- R:DEFAULT_FIXTURE A check is built from the DEFAULT precision, where a value that never travelled compares equal to one that did (Q4) -> "DEFAULT_FIXTURE"
- R:MOCK_ONLY_HONOUR M1 is proved by asserting a mock received an argument, with nothing showing the backend's own numerics changed -> "MOCK_ONLY_HONOUR"
</reject>

## LESSONS
- `select_backend` can return `device_type=CUDA` alongside `device_str="cpu"`: `_selector.py:335-345` sets the type from `torch_cuda_available` while `device_override` sets the string. Any capability decision taken from `BackendSelection.device_type` is taken from a field that can disagree with the device that runs. -> add learn sdd
- An inert field is not inert once it is plumbed. `_sweep.py` has swept `precision` across backends for releases, and because nothing consumed it every row measured an identical configuration — so `profile.precision` is a winner picked by FPS noise over indistinguishable runs, and `_load_tune_profile` wrote that noise into production configs. Plumbing the value turns accumulated noise into a real numerics request, which is why "wire it up" is never only additive. -> add learn sdd
- A reported value with no consumer is not cosmetic. `precision` was accepted, validated, threaded through selection, stored on a frozen dataclass and published by `health_report()` — five layers of apparatus, zero execution — and every layer made it look more real. -> add learn add
