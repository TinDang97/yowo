# interview 1 — reader-shutdown

## A1 [who]
- asked: the reader thread via `reconnect()`, which is the only caller today and the reason the rebind exists
- if wrong: and a third party may swap it, the handle needs a lock rather than a re-read.
- answered: confirm

## A2 [which]
- asked: the NEXT read after it, not the in-flight one — a read already blocked in FFmpeg cannot be redirected
- if wrong: a rebind is expected to interrupt a read in progress, which no capture API offers.
- answered: confirm

## A3 [when]
- asked: ONCE PER ITERATION at the top, so the window between rebind and observation is one read
- if wrong: and it should be per access, the difference is a handle that changes mid-iteration, which is harder to reason about, not easier.
- answered: confirm

## A4 [absent]
- asked: "cannot happen while iterating" — `__iter__` sets it before the loop and every path reassigns it — and asserting rather than silently substituting, since a None here means a bug elsewhere
- if wrong: the loop must tolerate a None and the tolerant version hides the bug.
- answered: confirm

## A5 [order]
- asked: the retry branch's own reopen as authoritative, since it assigns `_active_cap` too
- if wrong: a reconnect racing a retry produces two captures and orphans one, which is the very defect.
- answered: confirm

## A6 [experience]
- asked: an operator watching logs — the difficulty is that today a healthy stream emits "recovered after 1.0s" every reconnect interval, which trains them to ignore the line that matters
- if wrong: so a periodic reconnect must be silent about outages.
- answered: confirm

## A7 [who]
- asked: the READER, which acquired it by starting a thread over it
- if wrong: and the caller owns it, `stop()` must not close a source the caller intends to reuse.
- answered: confirm

## A8 [which]
- asked: the thread AND the source's captures, because those are what starting it acquired
- if wrong: the fd count is the caller's problem and the box's "counts return to baseline" is unsatisfiable by this class alone.
- answered: confirm

## A9 [when]
- asked: YES, since `__exit__` calls it and a caller may call it too
- if wrong: a double stop raises where a context manager already called it.
- answered: confirm

## A10 [absent]
- asked: a no-op rather than an error, matching the existing `if self._thread is not None` shape
- if wrong: error handling around a failed start gets harder.
- answered: confirm

## A11 [order]
- asked: AFTER, because the thread may still be inside a read and closing under it is the use-after-release this node exists to end
- if wrong: a hung thread holds the capture past `stop()`, which the join timeout already bounds.
- answered: confirm

## A12 [experience]
- asked: whoever cycles readers in a long-lived process — the difficulty is that a leaked thread is invisible until the process runs out
- if wrong: so a join that times out must say so rather than returning silently.
- answered: confirm

## R:ORPHAN [reject]
- asked: A capture left open and unreachable after a reconnect.
- answered: confirm

## R:FAKEOUTAGE [reject]
- asked: A reconnect that registers as an outage — budget, log line, or sleep.
- answered: confirm

## R:REFCOUNT [reject]
- asked: Relying on garbage collection to release a capture or join a thread.
- answered: confirm

## R:COUNTONLY [reject]
- asked: Proving the rebind is observed with a count check, which the box explicitly says cannot catch it.
- answered: confirm
