# interview 1 — rtsp-reconnect-correctness

## A1 [who]
- asked: the DEPLOYER's, unchanged — `reconnect_timeout_s` already exists and already means this, it simply does not work
- if wrong: and it should be global, the per-source parameter stays and is redundant.
- answered: confirm

## A2 [which]
- asked: BOTH a failed read and a failed reopen as the same outage, since from the camera's side they are one event and a caller cannot distinguish them
- if wrong: a reopen failure needs its own bound and its own parameter.
- answered: confirm

## A3 [when]
- asked: FIRST FAILURE of a contiguous outage, reset on the next successful read
- if wrong: and it measures stream lifetime, a healthy stream dies after `reconnect_timeout_s` regardless of health, which is absurd; recorded so the reading is visible.
- answered: confirm

## A4 [absent]
- asked: "do not retry at all — the first failure is terminal", which is the reading that makes 0 continuous with small values
- if wrong: 0 means unlimited and a caller asking for no retries gets infinite ones.
- answered: confirm

## A5 [order]
- asked: the BOUND — if the next sleep would cross the deadline the stream ends then, rather than sleeping past it and noticing late
- if wrong: the stream outlives its stated bound by up to one backoff interval.
- answered: confirm

## A6 [experience]
- asked: an operator deciding whether the camera or the config is at fault — the difficulty is that "timed out" alone cannot distinguish a dead camera from a bound set too low
- if wrong: so the message carries the elapsed time and the bound, not just the bound.
- answered: confirm

## A8 [which]
- asked: `SourceError` — the type it actually raises for an unopenable stream — and letting anything else propagate, since an unexpected exception type is not evidence the camera will return
- if wrong: a retryable condition raising something else ends the stream.
- answered: confirm

## A9 [when]
- asked: the existing check first, so a stream that has already yielded its quota ends normally rather than entering retry
- if wrong: a bounded capture can end with a timeout instead of cleanly.
- answered: confirm

## A10 [absent]
- asked: the existing behaviour — it raises before the loop and is not a reconnect — because a stream that never started has nothing to reconnect to
- if wrong: startup gets retry semantics it does not have today, which is a larger behaviour change than this node's subject.
- answered: confirm

## A13 [absent]
- asked: `None`, distinct from `0` which is zero tolerance, so the two edges are opposite and unambiguous
- if wrong: the capability that exists today is removed with no replacement, which is a breaking change on a 2.5.0 semver promise.
- answered: confirm

## A11 [order]
- asked: a successful READ, since a reopen that succeeds and then reads nothing is still the same outage and must not reset the backoff to zero
- if wrong: a camera that accepts connections but never sends frames loops fast forever.
- answered: confirm

## A12 [experience]
- asked: the consumer of the frame iterator — the difficulty is that a silent recovery is indistinguishable from a stall of the same length
- if wrong: so a recovery is observable, at minimum through the existing logging path, rather than silent.
- answered: confirm

## R:INERT [reject]
- asked: A bound a caller can set that does not change behaviour.
- answered: confirm

## R:DIESONBLIP [reject]
- asked: A single failed reopen ending the stream.
- answered: confirm

## R:SPIN [reject]
- asked: Removing the backoff cap, or retrying without delay.
- answered: confirm

## R:REALSLEEP [reject]
- asked: Proving a bound by sleeping through it.
- answered: confirm

## R:ORPHANFIX [reject]
- asked: Fixing the `reconnect()` capture orphan here.
- answered: confirm
