# interview 1 — capture-timeouts

## A1 [who]
- asked: the DEPLOYER's, set per source at construction, because the right wait for a camera on a LAN and one over a cellular backhaul differ by an order of magnitude and no library default can serve both
- if wrong: and it is a global setting, the per-source parameter is redundant but harmless.
- answered: confirm

## A2 [which]
- asked: 30000ms for both, which is what FFmpeg already applies, so behaviour is unchanged and only controllability is added
- if wrong: every existing deployment's tolerance for a camera blip changes on upgrade, which is R:SILENTSHORTEN.
- answered: confirm

## A3 [when]
- asked: PER ATTEMPT, matching what the property means to FFmpeg
- if wrong: a caller reading it as a lifetime budget gets a stream that outlives the number they set.
- answered: confirm

## A4 [absent]
- asked: None = "leave FFmpeg's default in place", distinct from 0 which FFmpeg reads as no-timeout, and documenting the difference
- if wrong: a caller passing None to mean "never time out" gets 30s instead.
- answered: confirm

## A5 [order]
- asked: them as independent key/value pairs in one params list, order irrelevant, because that is how `VideoCapture`'s params argument is specified
- if wrong: one silently overrides the other.
- answered: confirm

## A6 [experience]
- asked: an operator whose camera is down at 3am — the difficulty is that a 30-second stall with no output is indistinguishable from a hung process, so they kill it and lose the diagnosis
- if wrong: the raise must name the source (redacted) and the bound that was exceeded.
- answered: confirm

## A7 [who]
- asked: the same deployer, via whatever calls the factory — CLI or library — with the parameter simply passed through and not re-decided at each layer
- if wrong: the CLI needs its own flag, which is additive and does not change this contract.
- answered: confirm

## A8 [which]
- asked: NETWORK SOURCES ONLY. `cv2.VideoCapture(str(path))` and `cv2.VideoCapture(device_index)` use a non-FFMPEG backend where these properties are not honoured, so accepting them there would be a parameter that silently does nothing
- if wrong: a wedged NFS-mounted file still stalls, and that needs a different mechanism than this one.
- answered: confirm

## A9 [when]
- asked: validation at the factory boundary — a negative timeout is rejected where the caller can still see their own call, not deep inside a capture
- if wrong: a typo surfaces as a hang rather than as an error.
- answered: confirm

## A10 [absent]
- asked: the same default as S1, so the factory and the constructor cannot disagree
- if wrong: the same source built two ways waits two different lengths, which is the worst outcome for a thing whose whole subject is predictability.
- answered: confirm

## A12 [experience]
- asked: someone choosing a timeout for the first time — the difficulty is that milliseconds and seconds already coexist here (`reconnect_timeout_s` is seconds)
- if wrong: so the unit is in the parameter NAME, and the docstring states the measured default rather than describing it vaguely.
- answered: confirm

## A14 [which]
- asked: network captures in `src/yowo/io/` only, the sites where the property is honoured, so the gate cannot demand a parameter that would do nothing
- if wrong: the gate is narrower than "every capture" and says so explicitly rather than implying it.
- answered: confirm

## A15 [when]
- asked: BEHAVIOUR where it can — what the capture was constructed with — because a source-text scan passes on a correctly-spelled call that is never reached, which is method M9
- if wrong: and only text is feasible, the check says which it is rather than implying the stronger one.
- answered: confirm

## A16 [absent]
- asked: FAIL, because a gate that skips what it does not understand is a gate that the next unusual call slips past
- if wrong: an odd-but-safe construction needs an explicit, named exemption.
- answered: confirm

## A18 [experience]
- asked: whoever just added a capture — the difficulty is that "add a timeout" without the reason invites the smallest edit that silences it
- if wrong: so the message carries the measured 30.08s-versus-2.02s contrast that motivates the rule.
- answered: confirm

## R:HARDCODE [reject]
- asked: A timeout the caller cannot set.
- answered: confirm

## R:SILENTSHORTEN [reject]
- asked: Changing the effective default wait without a human deciding it.
- answered: confirm

## R:MOCKONLY [reject]
- asked: Proving the bound with a mocked `cv2` alone — that proves the argument was passed, not that it is honoured.
- answered: confirm

## R:PARTIAL [reject]
- asked: Bounding one construction site and leaving another bare.
- answered: confirm

## R:SCOPECREEP [reject]
- asked: Touching retry, backoff or the reconnect deadline here.
- answered: confirm
